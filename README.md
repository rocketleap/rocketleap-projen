# rocketleap-projen

This project provides projen templates to quickly set up CDK projects in the Rocketleap platform.
It automatically tracks the `building-blocks-cdk` making it easy to stay up to date.

## Features

- Pre-configured AWS CDK TypeScript project setup
- Automatic dependency management for `building-blocks-cdk`
- Standardized ESLint, Prettier, and Git configuration
- Yarn Berry (v4) with private registry support
- Pre-commit hooks for code quality

## How to adopt

### New project

Run `projen new` to create a new project:

```shell
npx projen new --from @rocketleap/rocketleap-projen --company "<company>" --project "<project>"
```

### Existing project

Existing projects can adopt the projen templates and get managed by `projen`.

1. Install the `rocketleap-projen` library and peer dependencies:

   ```shell
   yarn add -D @rocketleap/rocketleap-projen projen
   ```

2. Create or replace the `.projenrc.ts` file using the appropriate project type:

   ```typescript
   import { PlatformCdkProject } from '@rocketleap/rocketleap-projen';

   const project = new PlatformCdkProject({
     company: '<company>',
     project: '<project>',
   });

   project.synth();
   ```

3. Run projen to generate the project configuration:

   ```shell
   npx ts-node .projenrc.ts
   ```

## Project Types

### PlatformCdkProject

Use for **platform infrastructure** code (e.g., root-cdk, vpc-cdk, iam-cdk, security-cdk).

- Includes the Norberhuis Onderneming B.V. IaC License
- For code that is part of the licensed platform

```typescript
import { PlatformCdkProject } from '@rocketleap/rocketleap-projen';

const project = new PlatformCdkProject({
  company: 'rocketleap',
  project: 'root-cdk',
});

project.synth();
```

### WorkloadCdkProject

Use for **customer workload** code that runs on the platform.

- Does NOT include the platform license
- For customer-specific application infrastructure

```typescript
import { WorkloadCdkProject } from '@rocketleap/rocketleap-projen';

const project = new WorkloadCdkProject({
  company: 'acme',
  project: 'my-app-cdk',
});

project.synth();
```

### RocketleapCdkProject (Base)

The base class used by both project types. Can be used directly if you need custom license handling.

## Options

| Option                  | Required | Default     | Description                                     |
| ----------------------- | -------- | ----------- | ----------------------------------------------- |
| `company`               | Yes      | -           | The company identifier used for package scoping |
| `project`               | Yes      | -           | The project name                                |
| `cdkVersion`            | No       | `'2.232.1'` | The AWS CDK version to use                      |
| `constructVersion`      | No       | `'10.4.4'`  | The constructs library version                  |
| `buildingBlocksVersion` | No       | `'0.104.1'` | The Rocketleap building blocks CDK version      |

### Extending `.gitignore`

Pass `gitignore` to add patterns on top of the Rocketleap defaults (e.g. for a workload that bundles Python alongside the CDK):

```typescript
new WorkloadCdkProject({
  company: 'acme',
  project: 'my-app-cdk',
  gitignore: ['.venv/', 'pyproject.toml.bak'],
});
```

Your patterns are prepended to the Rocketleap defaults and duplicates are dropped.

## Generated scripts

Every project generated by `PlatformCdkProject` / `WorkloadCdkProject` gets these `package.json` scripts. Most take a positional argument: the **deployment** — the env name (`bin/<env>.ts`) or the `env/workload` pair (`bin/<env>/<workload>.ts`). Under Yarn, `$0` is the first positional argument.

**Convention — the `:ci` variants are the versions used by CI pipelines and pre-commit hooks.** The plain scripts (`format`, `deploy`, `diff`, ...) are developer-facing and often interactive; the `:ci` scripts are non-interactive, fail fast, and take slightly different arguments matched to what the generated GitHub Actions workflows pass in. Use the plain scripts locally; the pipeline calls the `:ci` scripts.

### Format

Prettier keeps every file consistent. Prefer configuring format-on-save in your IDE — the scripts are the fallback.

| Script | What it does |
| --- | --- |
| `format` | Runs Prettier in write mode over the codebase. |
| `format:ci` | Runs Prettier in check mode; fails if any file needs formatting. Used by `action-build.yml`. |

### Lint

ESLint surfaces bugs and enforces coding standards. Configure ESLint in your IDE to see warnings inline; the scripts are the fallback.

| Script | What it does |
| --- | --- |
| `lint` | Runs ESLint with `--fix` on the codebase. |
| `lint:ci` | Runs ESLint with `--max-warnings=0`; any warning fails CI. Used by `action-build.yml`. |

### Build & clean

CDK runs TypeScript directly via `ts-node`, so a compile step isn't strictly required for `cdk synth` / `cdk deploy`. But if the project bundles Lambda handlers in TypeScript, those need JavaScript — and stale `.js` files from a previous build can leak into tests, so `clean` matters.

| Script | What it does |
| --- | --- |
| `build` | `tsc` — compiles TypeScript to JavaScript. |
| `clean` | Removes compiled `.js` and `.d.ts` files under `bin/`, `src/`, `test/`. |
| `watch` | `tsc -w` — recompiles on file change. |

### Test

Jest runs unit + snapshot tests. Snapshot tests capture the synthesized CloudFormation so infra changes are surfaced in review.

| Script | What it does |
| --- | --- |
| `test` | Runs the Jest suite. |
| `test:ci` | `jest --ci` — no interactive prompts, used by `action-build.yml`. |
| `test:update-snapshots` | `jest --updateSnapshot` — regenerates snapshots when infra changes are intentional. |

### Synth

Synthesizes the CDK app into a CloudFormation cloud assembly under `cdk.out/<env>[/<workload>]/`. Per-env output directories keep parallel synth from stomping on each other.

| Script | What it does |
| --- | --- |
| `synth <env>[/<workload>]` | `cdk synth --output cdk.out/$0/ --app "yarn ts-node ... bin/$0.ts"`. Example: `yarn synth dev`, `yarn synth platform/management`. |
| `synth:ci <app-file>` | `cdk synth --ci --app "yarn ts-node ... $0"`. Legacy shape; used by the legacy `action-diff.yml`. |

### Bootstrap

CDK needs bootstrap resources (an S3 bucket, IAM roles) in each `<account, region>` before it can deploy. Run once per account/region.

| Script | What it does |
| --- | --- |
| `bootstrap <env>[/<workload>]` | `cdk bootstrap` against the account/region pinned in the given entry point. |

### List

| Script | What it does |
| --- | --- |
| `list <env>[/<workload>]` | Lists every stack in the deployment. Useful when picking a stack to deploy in isolation. |

### Diff

Compares the deployed CloudFormation with the current synthesized state. Run this before every deploy.

| Script | What it does |
| --- | --- |
| `diff <env>[/<workload>] [<stack>]` | `cdk diff` for the deployment. Optional second arg targets a single stack. |
| `diff:ci <app-file>` | `cdk diff --ci`. Used by the legacy `action-diff.yml`. The stages pipeline uses `corymhall/cdk-diff-action` instead, which reads the pre-synthed cdk.out directly. |

### Deploy

Deploys to AWS. Prefer running `diff` first so you know what's about to change.

| Script | What it does |
| --- | --- |
| `deploy <env>[/<workload>] [<stack>]` | `cdk deploy --require-approval never`. Optional second arg targets a single stack. |
| `deploy:ci <cdk-out-dir>` | Deploys from a pre-synthed cloud assembly (`cdk.out/<env>[/<workload>]`). Used by both the legacy and the stages `action-deploy.yml` — each first runs `yarn synth <env>[/<workload>]` (or downloads the stage's `cdk-out-<env>[-<workload>]` artifact in stages mode) so `cdk.out/` is populated before this script runs. |

### Destroy

Removes deployed stacks. Destructive.

| Script | What it does |
| --- | --- |
| `destroy <env>[/<workload>] [<stack>]` | `cdk destroy`. Optional second arg targets a single stack. |
| `destroy:ci <app-file>` | `cdk destroy --ci -f --all` for cleanup workflows. |

## Pipeline

Every project sets `pipeline` on the project options. By default (`PromotionStrategy.PR`) the generator emits nine GitHub Actions workflows: the reusable `action-build.yml`, `action-synth.yml`, `action-deploy.yml`, `action-diff.yml` and `action-promote-pr.yml`, plus `pr-main.yml` / `push-main.yml` triggered by `main` and `dev` and `pr-production.yml` / `push-production.yml` triggered by `production`. The branches are fixed.

```typescript
pipeline: {
  stages: [
    { environment: 'dev' },
    { environment: 'staging' },
    { environment: 'prodeu', promotion: true },
    { environment: 'produs', promotion: true },
  ],
},
```

Each entry is a `PipelineStage`, mapping to the CDK app file `bin/<environment>.ts` or `bin/<environment>/<workload>.ts`:

| Field | Type | Default | Purpose |
| --- | --- | --- | --- |
| `environment` | `string` | required | CDK app file segment and GitHub Environment name. |
| `workload` | `string` (optional) | none | Workload name for multi-app projects. |
| `promotion` | `boolean` (optional) | `false` | Deploy the stage only after the promotion PR is merged. At least one stage must set it under `PromotionStrategy.PR`. |
| `diff` | `boolean` (optional) | `true` | Synth and diff the stage on pull requests. Set `false` to remove the stage from every pull request workflow, for a stage whose account is torn down or not reachable from CI. Deploys are unaffected. At least one stage must keep it enabled. |
| `wave` | `string` (optional) | the stage's `environment` | Deploy wave. Consecutive stages with the same wave deploy in parallel behind one gate on the GitHub Environment named after the wave, so the wave is approved once. Waves run in configured order. |

Pull requests into `main` or `dev` synth and diff every stage in configured order. Under `PromotionStrategy.PR` the promotion PR into `production` synths and diffs only the stages marked `promotion: true`. `diff: false` excludes a stage from both.

- `push-main.yml` deploys the stages without `promotion` on every push to `main` or `dev`, then opens its own timestamped promotion PR that promotes the pushed branch onto `production`. Promotion PRs are merged in order.
- `push-production.yml` deploys the stages marked `promotion: true` when the promotion PR is merged into `production`.

Promoted stages deploy in their listed order after the unpromoted ones, whatever their position in `stages`. A pipeline with only promoted stages is valid: `push-main.yml` then runs `build` and opens the promotion PR straight away.

`promotionStrategy: PromotionStrategy.DIRECT` keeps the single-branch shape with six files instead; see [`promotionStrategy`](#promotionstrategy--how-a-change-reaches-production) below.

Each push workflow deploys its stages sequentially in the order listed, unless they share a `wave`. Every deploy job sets `environment: <environment>` at the job level; configure required reviewers on the corresponding GitHub Environment in repo settings to gate that tier. Consecutive same-`environment` stages deploy in parallel under one gate (e.g. `{ environment: 'platform', workload: 'management', promotion: true }` followed by `{ environment: 'platform', workload: 'security', promotion: true }` fan out under a single `platform` gate); between-env promotion stays sequential.

Set `wave` to deploy stages of different environments in parallel. Consecutive stages with the same `wave` form one wave with one gate job. The gate uses the GitHub Environment named after the wave, so the wave is approved once, and every deploy in the wave starts together after that approval. The next wave waits for every deploy of the previous one. GitHub creates the wave's Environment on the first run; configure its required reviewers in repo settings.

```ts
stages: [
  { environment: 'dev' },
  { environment: 'staging' },
  { environment: 'maineu', promotion: true, wave: 'production' },
  { environment: 'mainus', promotion: true, wave: 'production' },
  { environment: 'prodeu', promotion: true, wave: 'production' },
  { environment: 'produs', promotion: true, wave: 'production' },
],
```

Here `maineu`, `mainus`, `prodeu` and `produs` deploy in parallel once the promotion PR is merged and the single `production` gate is approved. Configure the required reviewers on the `production` Environment. Without `wave` each environment is its own sequential step. Promoted and unpromoted stages deploy from different workflows, so a wave shared between them forms two waves, one per workflow.

### `cdkDiff` — customize the `corymhall/cdk-diff-action` step

`pipeline` accepts an optional `cdkDiff` field of type `CdkDiffOptions`:

```typescript
pipeline: {
  stages: [...],
  cdkDiff: { failOnDestructiveChanges: true },
}
```

| Field | Type | Default | Purpose |
| --- | --- | --- | --- |
| `failOnDestructiveChanges` | `boolean` (optional) | `false` | Fail the diff workflow when destructive changes are detected. The default surfaces destructive changes in the rich PR comment for reviewer attention without blocking the workflow — the required-reviewer gate on the corresponding GitHub Environment is what blocks the deploy. Set to `true` to make destructive changes a hard fail on PR CI. |

### `promotionStrategy` — how a change reaches production

`pipeline.promotionStrategy` chooses between two pipeline shapes. Both are generated from the same jobs; the difference is how many branches they are spread over.

| Value | Shape |
| --- | --- |
| `PromotionStrategy.PR` (default) | Two branch pairs with a promotion PR between them. Stages without `promotion` deploy from `main` and `dev`; `push-main.yml` then opens the PR onto `production`, and merging it deploys the stages marked `promotion: true`. |
| `PromotionStrategy.DIRECT` | One branch pair carries every stage. `pr-main.yml` diffs all stages and `push-main.yml` deploys all of them, pre-prod through prod, behind the required reviewers on each stage's GitHub Environment. Fewest moving parts and the fastest path to prod. |

Which one fits depends on the GitHub plan:

| GitHub plan | Required reviewers on Environments | Recommended |
| --- | --- | --- |
| Free / Team | Not enforced on private repositories | `PR` |
| Enterprise | Enforced | `DIRECT` or `PR` |

`DIRECT` gates only block on GitHub Enterprise; on other plans the gate job runs without approval.

#### PR promotion

```typescript
pipeline: {
  stages: [
    // Deployed from `main` and `dev`.
    { environment: 'dev' },
    { environment: 'staging' },
    // Deployed from `production`, once the promotion PR is merged.
    { environment: 'prodeu', promotion: true },
    { environment: 'produs', promotion: true },
  ],
},
```

The branches are fixed: pushes and pull requests to `main` and `dev` run the source workflows, and `production` is the promotion target.

`PromotionStrategy.PR`, the default, needs at least one stage marked `promotion: true`. `PromotionStrategy.DIRECT` rejects `promotion: true` on a stage. Both are synth-time errors, so a half-configured promotion fails `npx projen` rather than merging and then deploying the wrong stages.

What a change goes through:

1. **PR into `main` or `dev`**: `pr-main.yml` diffs every stage, the promoted ones included, so reviewers see the production diff before the change lands. Stages with `diff: false` are skipped.
2. **Merge to `main` or `dev`**: `push-main.yml` deploys the pre-prod stages behind their Environment gates.
3. **Promotion PR opens itself**: once every pre-prod stage has deployed, `push-main.yml` calls `action-promote-pr.yml`, which opens a new promotion PR from a timestamped `promote-<branch>-to-production-<timestamp>` branch onto `production`, where `<branch>` is the pushed `main` or `dev`. Each promotion is its own PR, and promotions are merged in order. The PR body lists the promoted commit and the commits since `production`.
4. **The promotion PR is the gate**: `pr-production.yml` diffs the stages marked `promotion: true`, except those with `diff: false`, against the current production state. That diff is the production change under review. The review, the diff and the merge are the durable record of who approved which production change, which is what `DIRECT` has no artefact for.
5. **Merge to `production`**: `push-production.yml` deploys the stages marked `promotion: true` in their listed order, still behind their Environment gates.

Adopting this in an existing repo is not just a projen change. `production` has to exist, and branch protection on it is what makes the promotion PR a real gate rather than a formality:

- Create `production` from `main` if it does not exist. Do not change the default branch; `main` stays the default.
- Require a review on `production` so the promotion PR is a real gate.

`promote` needs the last pre-production deploys, so a failed pre-production deploy does not open the promotion PR. With no unpromoted stages it needs `build` and the additional checks instead. Remove a stage from `pipeline.stages` when its account is torn down, and re-run `push-main.yml` via `workflow_dispatch` after a transient failure.

##### Promotion token

Since June 2026 GitHub runs workflows on pull requests opened by `github-actions[bot]` only after a user approves them. With the default `GITHUB_TOKEN` the promotion PR is opened by that bot, so the `pr-production.yml` run on it shows "action required" under Actions and the production diff is only posted after someone approves the run.

`push-main.yml` forwards three optional secrets to `action-promote-pr.yml`, which checks out, pushes the promotion branch and opens the PR with the first token available:

1. **GitHub App (preferred)**: create a GitHub App with `contents: write` and `pull-requests: write`, install it on the repos, and create the organization secrets `PROMOTION_APP_ID` (the App ID) and `PROMOTION_APP_PRIVATE_KEY` (a private key of the App). The workflow mints a short-lived installation token for the current repo on every run.
2. **PAT (simple alternative)**: create a repository or organization secret `PROMOTION_TOKEN` holding a fine-grained PAT, ideally of a machine user, with `contents: write` and `pull-requests: write` on the repo.
3. **`GITHUB_TOKEN` (fallback)**: without either secret the flow still works, but someone must approve each diff run on the promotion PR.

The PR author becomes the token's identity, so with a PAT that user cannot also be the required reviewer on `production`.

#### Migrating an existing pipeline

A pipeline with no stage marked `promotion: true` fails `npx projen` with `At least one pipeline stage must set promotion: true.` Pick one of the following.

Multi-stage repo: add `promotion: true` to every production stage.

```typescript
// Before
pipeline: {
  stages: [{ environment: 'dev' }, { environment: 'staging' }, { environment: 'prodeu' }, { environment: 'produs' }],
}

// After
pipeline: {
  stages: [
    { environment: 'dev' },
    { environment: 'staging' },
    { environment: 'prodeu', promotion: true },
    { environment: 'produs', promotion: true },
  ],
}
```

Single-stage repo: keep the single-branch pipeline.

```typescript
// Before
pipeline: {
  stages: [{ environment: 'iam' }],
}

// After
pipeline: {
  stages: [{ environment: 'iam' }],
  promotionStrategy: PromotionStrategy.DIRECT,
}
```

## Generated GitHub Actions workflows

Under `PromotionStrategy.PR`, the default, the generator emits nine files: the four reusable workflows below, `action-promote-pr.yml`, `pr-main.yml` / `push-main.yml` triggering on `main` and `dev`, and `pr-production.yml` / `push-production.yml` triggering on `production` alone.

| File | Purpose |
| --- | --- |
| `action-promote-pr.yml` | Reusable. Opens a new promotion PR against `production` from a timestamped `promote-<branch>-to-production-<timestamp>` branch reset onto the pushed `main` or `dev`, via `peter-evans/create-pull-request`. Each promotion is its own PR, and promotions are merged in order. The PR body lists the promoted commit and the commits since `production`. Called by `push-main.yml` after every unpromoted stage has deployed, which forwards the optional `PROMOTION_APP_ID`, `PROMOTION_APP_PRIVATE_KEY` and `PROMOTION_TOKEN` secrets; see [Promotion token](#promotion-token). |
| `pr-main.yml` / `pr-production.yml` | On PR to `main`/`dev` or to `production`: `build` → `synth` (matrix) → per-stage `diff`. `pr-main.yml` diffs every stage; `pr-production.yml` diffs the stages marked `promotion: true` against the current production state. Both skip stages with `diff: false`. |
| `push-main.yml` | On push to `main`/`dev`: `build` → `synth` → deploy chain for the stages without `promotion` → `promote`. With no unpromoted stages, `build` → `promote`. |
| `push-production.yml` | On push to `production`: `build` → `synth` → deploy chain for the stages marked `promotion: true`. |

Under `PromotionStrategy.DIRECT` it emits six files:

| File | Purpose |
| --- | --- |
| `action-build.yml` | Reusable. install → projen drift check → format/lint/tsc/test → upload `build-workspace` artifact (excluding `node_modules`, which the downstream synth reinstalls). |
| `action-synth.yml` | Reusable. Downloads `build-workspace`, reinstalls dependencies, runs `yarn synth <env>[/<workload>]`, uploads a per-stage `cdk-out-<env>[-<workload>]` artifact. |
| `action-deploy.yml` | Reusable. Downloads the stage's `cdk-out-<env>[-<workload>]` artifact, assumes `CdkDeployRole`, then `yarn run deploy:ci "cdk.out/<env>[/<workload>]"`. Job carries `environment: <env>` for the GitHub Environment gate. |
| `action-diff.yml` | Reusable. Downloads the stage's cdk.out artifact, runs `corymhall/cdk-diff-action@v2` with `noSynth: true` and posts a rich diff comment on the PR. |
| `pr-main.yml` | On PR to `main`/`dev`: `build` → `synth` (matrix over every stage except those with `diff: false`, parallel) → per-stage `diff` (each waits on `synth`). |
| `push-main.yml` | On push to `main`/`dev`: `build` → `synth` (matrix) → deploy chain grouped by `environment`. Consecutive same-env stages deploy in parallel under one gate; between-env promotion is sequential. |

`push-main.yml` keeps the name `Push: Main Branch` and its `main`/`dev` triggers under both strategies, so `workflow_run` listeners on that name keep working. Under `PR` it deploys the pre-prod stages and opens the promotion PR; `push-production.yml` is named `Push: Production Branch`.
